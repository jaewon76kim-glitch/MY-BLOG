## 왜 이런 구조가 필요했나

이 블로그는 WSL 위에서 Claude Code로 만들지만, 물리·위성통신·머신러닝 같은 개인 PDF 교재들은 Windows에서 Claude Cowork로 따로 만들어왔습니다. 처음엔 이 둘을 완전히 분리된 두 세계로 다뤘습니다 — Cowork 쪽은 교재 집필, WSL 쪽은 블로그. 문제는 블로그 글감을 Cowork 쪽 자료(예: OS 역사 교재, 위성통신 표준 정리)에서 가져다 쓰기 시작하면서 생겼습니다. 두 세계가 자연스럽게 얽혔는데, 그 연결을 규칙으로 정리해둔 게 없었습니다.

결정적인 계기는 따로 있었습니다. Cowork 쪽 폴더 하나를 정리하다가, **가족과 관련된 개인적인 프로젝트 하나가 같은 폴더 트리 밑에 섞여 들어와 있다는 걸 발견**했습니다. 이 블로그는 GitHub 공개 저장소로 push되는데, 만약 블로그 소재를 가져오는 과정에서 그 폴더 내용이 실수로라도 딸려 들어온다면 되돌릴 수 없습니다. "어느 자료는 가져다 써도 되고, 어느 자료는 절대 안 되는가"를 명시적으로 정리해야 한다는 게 분명해진 순간이었습니다.

여기에 더해 실무적인 문제도 하나 있었습니다. WSL의 Claude Code에는 LaTeX 컴파일 도구(xelatex)가 아예 없어서, "이 작업은 어디서 해야 하는가"라는 질문이 계속 반복됐습니다. 이 두 문제 — **역할 분리**와 **프라이버시 경계** — 를 한 문서로 풀기 위해 만든 게 최상위 오케스트레이터입니다.

## 전체 그림

```
 (나)
   │ 지시
   ▼
 오케스트레이터 — Projects/orchestrator/CLAUDE.md
   │   프로젝트 레지스트리 + 프라이버시 경계 + 핸드오프 절차
   │
   ├──▶ doc (Windows, Claude Cowork)
   │      CLAUDE.md(루트) — 하위 7개 CLAUDE.md(PDF 교재 6권 + 요약노트)
   │      저장: Google Drive
   │
   ├──▶ doc/개인 프로젝트 (Cowork, ⚠️ 비공개)
   │      CLAUDE.md + 참고자료.md — 민감한 개인정보 포함
   │      "공개 프로젝트로 절대 옮기지 않는다"(프라이버시 규칙)
   │
   └──▶ MY_BLOG (WSL, Claude Code) ← 지금 이 글을 쓰는 곳
          CLAUDE.md
          ├─ .claude/skills/post-article/SKILL.md   (글 게시 워크플로우)
          ├─ .claude/skills/myblog-harness/SKILL.md (하네스 스냅샷)
          ├─ posts/index.json + scripts/validate_posts.py
          └─ git push → GitHub public repo

 (모든 프로젝트를 가로지르는 두 축)
   MCP(Google Drive 도구) — WSL에서 로컬 동기화 없이 Cowork Drive 자료에 직접 접근
   메모리 — 세션이 끝나도 남는 것. ~/.claude/.../memory/*.md + MEMORY.md 색인
           타입: user · feedback · project · reference
```

박스 세 개(doc, 개인 프로젝트, MY_BLOG)가 각각 다른 환경(Windows Cowork vs WSL Claude Code)과 다른 저장 방식(Google Drive vs git)을 쓰는데, 이걸 하나의 문서에서 총괄하는 게 오케스트레이터입니다. 그리고 이 그림 어디에도 안 들어가지만 모든 걸 가로지르는 두 가지 — MCP와 메모리 — 가 있습니다. 하나씩 보겠습니다.

## CLAUDE.md — 규칙이 쌓이는 계층

`CLAUDE.md`는 Claude Code/Cowork가 세션을 시작할 때 자동으로 읽는 지침 파일입니다. 지금 이 생태계에는 이게 계층적으로 쌓여 있습니다.

```
오케스트레이터 CLAUDE.md (최상위)
   └─ doc/CLAUDE.md (프로젝트 루트)
        └─ doc/위성통신/CLAUDE.md (하위 폴더, 이 책만의 규칙)
```

거의 모든 CLAUDE.md에 공통으로 박혀 있는 문구가 하나 있습니다 — "사용자가 직접 이 파일을 수정하지 않아도, 새 요청/지침이 생기면 Claude가 대화 중 이 파일을 직접 갱신한다." 문서가 낡는 걸 막으려는 장치인데, 최근에 전체를 감사해보니 이 장치만으로는 부족하다는 것도 확인했습니다. PDF 교재 6권의 CLAUDE.md에 컴파일 절차·LaTeX 스타일 같은 규칙이 거의 그대로 복제돼 있어서, 절차 하나가 바뀌면 6곳을 다 고쳐야 하는 상태였습니다. 지금은 doc 루트에 "PDF 교재 공통 규칙"을 한 곳에 모으고, 하위 6개 파일은 그 규칙을 가리키기만 하도록 정리했습니다 — 규칙도 코드처럼 중복이 쌓이면 유지보수 부채가 됩니다.

## 메모리 — 대화가 끝나도 남는 것

CLAUDE.md가 "이 프로젝트에서 지킬 규칙"이라면, 메모리는 "대화 세션이 끝나도 남아야 할 사실"입니다. 파일 기반으로 동작하고, 네 가지 타입으로 나뉩니다.

| 타입 | 담는 내용 |
|---|---|
| **user** | 내가 누구인지, 어떤 배경·전문성을 가졌는지 |
| **feedback** | "이렇게 하지 마라"/"이 방식은 계속 유지해라"처럼 교정·확인받은 작업 방식 |
| **project** | 지금 진행 중인 일의 맥락(마감, 결정 배경 등) |
| **reference** | 다른 시스템(Notion DB, Linear 프로젝트 등)을 가리키는 포인터 |

각 메모리는 frontmatter가 있는 개별 markdown 파일이고, `MEMORY.md`가 한 줄씩 요약하는 색인 역할을 합니다. 예를 들어 "가족 관련 개인 프로젝트가 정확히 어느 위치에 있고 어떤 규칙이 적용되는지"가 메모리에 기록되어 있어서, 다음에 이 이야기가 나오면 매번 처음부터 설명할 필요가 없습니다. 오케스트레이터를 만드는 과정에서 겪은 시행착오(예: Google Drive API로 새 폴더를 만들면 자주 실패한다는 것)도 메모리에 남겨뒀는데, 이런 세부 운영 노하우야말로 메모리가 진짜 유용해지는 지점입니다 — 같은 삽질을 다음에 또 하지 않게 해줍니다.

## 스킬 — 반복 작업의 캡슐화

스킬은 "이 종류의 작업은 항상 이 순서로 한다"를 문서화한 것입니다. 이 블로그엔 두 개가 있습니다.

- **post-article** — 글 하나를 올릴 때의 절차(주제 확정 → 승인 → 작성 → 자체 검증 → 커밋/푸시)를 정의합니다. 특이한 점 하나: 다른 작업은 전부 "승인 없이 시작하지 않는다"가 기본인데, 글 게시만큼은 검증을 통과하면 승인 없이 바로 커밋·푸시까지 진행하도록 예외를 뒀습니다(제가 그렇게 요청했었습니다).
- **myblog-harness** — 이 프로젝트가 어떤 규칙·기술스택·권한 설정 아래 돌아가는지 한 번에 브리핑하는 "스냅샷" 스킬입니다. 새 세션이나 외부 도구에게 통째로 맥락을 넘길 때 씁니다.

스냅샷 스킬에는 함정이 하나 있습니다 — 원본(CLAUDE.md, 설정 파일)이 바뀌면 스냅샷도 같이 갱신해야 하는데, 이번에 전체를 감사해보니 최근에 추가한 카테고리와 프라이버시 규칙이 스냅샷엔 반영이 안 돼 있었습니다. 스킬 자신이 "원본 바뀌면 반드시 갱신할 것"이라고 명시해뒀는데도요. 수동 동기화는 결국 이렇게 새어나간다는 걸 실제로 확인한 셈입니다.

## MCP — Cowork와 Claude Code를 잇는 다리

MCP(Model Context Protocol)는 Claude가 외부 도구·데이터에 접근하는 표준 방식입니다. 여기서 중요하게 쓰인 건 Google Drive용 MCP 도구입니다.

원래는 "WSL에서 Cowork 자료를 보려면 로컬 폴더에 동기화될 때까지 기다려야 한다"고 생각했습니다. 그런데 실제로 해보니, **로컬 동기화가 안 된 상태에서도 Google Drive API 도구로 파일을 바로 읽고 쓸 수 있었습니다.** 폰으로 파일을 옮긴 직후 로컬 폴더에는 한참을 기다려도 안 보였는데, Drive API로는 바로 조회가 됐습니다. 덕분에 "Windows PC 앞에 있지 않아도 Cowork 쪽 자료를 다룰 수 있다"는 게 실제로 가능해졌습니다.

다만 한계도 있었습니다. 이 도구로 새 폴더를 만들거나 긴 텍스트를 한 번에 쓰려고 하면 종종 원인 불명의 오류가 났고, 애초에 파일을 지우는 기능 자체가 없었습니다. 그래서 지금은 "새 폴더가 필요하면 로컬 파일시스템에 직접 만들고, 기존 폴더 안에 파일을 추가할 때만 Drive API를 쓴다"는 식으로 역할을 나눠 씁니다.

## 프라이버시 경계 — 왜 필요했나

앞서 말한 "가족 관련 개인 프로젝트"가 이 구조 전체의 존재 이유입니다. 이 프로젝트는 실명·성적 등 민감한 개인정보를 담고 있고, doc 프로젝트 폴더 아래 들어와 있습니다. 반면 이 블로그(MY_BLOG)는 GitHub 공개 저장소입니다. 둘 다 "doc 프로젝트에서 소재를 가져온다"는 같은 파이프라인을 타기 때문에, 폴더 구분을 안 하면 개인정보가 공개 저장소로 새어나갈 위험이 실제로 있었습니다.

그래서 오케스트레이터의 프로젝트 레지스트리에 "공개/비공개" 열을 명시적으로 두고, 이 규칙을 오케스트레이터 한 곳에만 적어두지 않고 **관련된 모든 CLAUDE.md(doc 루트, 그 개인 프로젝트 폴더, MY_BLOG, 그리고 myblog-harness 스킬까지)에 반복해서** 적어뒀습니다. 한 곳에만 적어두면 그 한 곳이 고장 났을 때(예: 새 세션이 그 파일을 안 읽고 시작했을 때) 바로 뚫리기 때문입니다 — 단일 지점 실패를 피하는 가장 단순한 방법은 결국 같은 규칙을 여러 곳에 심어두는 것이었습니다.

## 핸드폰 원격 작업지시 — Tailscale + tmux

이 부분은 몇 주 전에 [별도 글](post.html?slug=remote-control-claude-code-with-tailscale)로 이미 정리해뒀어서, 여기선 핵심만 다시 짚습니다.

```
 폰(SSH 클라이언트 앱)
   │  Tailscale — WireGuard 기반 VPN, 공유기 포트포워딩·공인 IP 노출 없음
   ▼
 PC(WSL, sshd 리스닝 중)
   │
   ▼
 tmux 세션 "main" — systemd 서비스로 상시 유지, WSL 부팅 시 자동 생성
   │
   ▼
 claude 실행
```

핵심은 두 가지입니다. 첫째, 포트포워딩이나 공인 IP 없이 Tailscale 하나로 폰과 PC를 같은 사설망처럼 묶습니다. 둘째, tmux 세션을 서버(WSL) 쪽에 상시 띄워두기 때문에, 폰 화면이 꺼지거나 앱이 종료돼도 Claude Code 세션 자체는 계속 살아있습니다 — 나중에 다시 접속하면 그대로 이어받습니다. 이 구조 덕분에 지금 이 글도 포함해서, PC 앞이 아니어도 오케스트레이터 전체를 조작할 수 있습니다.

## 정리

정리하면 이 생태계는 네 가지 장치로 굴러갑니다. **CLAUDE.md**가 "무엇을 지켜야 하는가"를 계층적으로 쌓고, **메모리**가 "대화가 끝나도 남아야 할 사실"을 붙잡고, **스킬**이 "반복되는 작업 순서"를 캡슐화하고, **MCP**가 "서로 다른 환경(Cowork/Claude Code) 사이의 다리"를 놓습니다. 그리고 이 네 가지를 하나로 묶는 오케스트레이터의 진짜 존재 이유는 결국 하나였습니다 — 비공개로 남아야 할 것이 공개로 새어나가지 않게 하는 것.

흥미로운 건 이 감사 과정 자체가 이 구조의 약점도 같이 드러냈다는 점입니다. "원본이 바뀌면 스냅샷도 갱신하라"는 규칙이 스킬 파일에 명시돼 있었는데도 실제로는 안 지켜졌던 것처럼, 수동 동기화 관례는 결국 어딘가에서 새어나갑니다. 지금은 그걸 발견할 때마다 고치는 식으로 굴러가고 있는데, 다음 단계는 아마 이런 드리프트를 사람이 발견하기 전에 자동으로 잡아내는 장치일 것 같습니다.
